# 站点适配库 · sites/

这里存放**按站点**的填写规则。

字段规则库（`assets/字段规则_通用.json`）解决的是「这个框叫什么名字」；
站点适配库解决的是「这个框在这台戏里长什么样、它的下拉选项该怎么选」。

---

## 一、为什么需要第二层

先看一个真实会遇到的场景。

你的档案里写的是：

```
最高学历 = 硕士
政治面貌 = 中共党员
```

而某个网申系统的下拉框里，选项文案是：

```
全日制普通高等教育研究生(硕士)
中国共产党党员
```

**这不是「认不认识这个词」的问题，是「值域怎么对应」的问题。**

| 层 | 解决的问题 | 可复用范围 |
|---|---|---|
| 字段规则库 | 「真实姓名」也指姓名、「Mobile」也指手机号 | 全网站点通用 |
| **站点适配库** | 这个站点的「硕士」写着「全日制…研究生(硕士)」 | **该站点专属** |

第二层**只能靠踩过这个站点的人贡献**——这正是本目录存在的意义。

---

## 二、怎么贡献（三步）

### 1. 复制格式示例

```bash
cp sites/_示例.json sites/<目标域名>.json
```

文件名就是域名，例如 `portal.abc.com.json`。

### 2. 按规范填写

字段含义见 [`_schema.json`](_schema.json)。最少只需要填两项：

```json
{
  "域名": "portal.abc.com",
  "字段选择器": {
    "姓名": "#realName",
    "手机号": "#mobile"
  }
}
```

如果这个站点的下拉文案跟档案值不一致，**加上 `选项映射`——这是最有价值的部分**：

```json
{
  "选项映射": {
    "最高学历": { "硕士": "全日制普通高等教育研究生(硕士)" }
  }
}
```

### 3. 提 PR 前跑自检

```bash
python scripts/dist_check.py
```

**必须看到 `FAIL 0 项`。** 这条检查会扫出「不小心把真实信息写进规则文件」——这是本目录唯一会让整个项目出事的方式。

---

## 三、三条硬约束

违反任何一条，PR 会被拒绝。

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **不含任何真实个人值** | 本目录会随仓库分发给所有使用者。姓名、身份证号、手机号、经历正文一律不许出现 |
| 2 | **不含绕过登录 / 验证码 / 风控的手段** | 这三件事永远留给真人。工具的价值是「不替你做决定」，不是「替你做所有事」 |
| 3 | **选择器写结构性依据** | 优先 `id` / `name`，其次层级关系。**不要用颜色、坐标、序号**——站点一改版就失效 |

---

## 四、为什么这里只放「与人无关」的东西

一句话可以判断：**把文件里的内容换成另一个人的，它还能用吗？**

- 能用 → 与人无关 → 放这里 ✓
- 不能用 → 含个人数据 → **绝不放进仓库** ✗

`scripts/dist_check.py` 就是在机械化执行这句话。

---

## 五、失效了怎么办

站点改版会让老规则失效，这是必然会发生的——**规则库会腐烂，这是它的固有属性，不是缺陷。**

发现某个站点填不上时，请：

1. 提 Issue，附上报错和当前页面结构（**注意脱敏**）
2. 或者直接更新那个 `.json`，把失效的选择器修正掉

> 站点改版时，`_贡献时间` 字段能帮后来者判断「这条规则是不是很久没动了」。
> 顺手更新它，成本很低。
